# インセプションデッキ
- status: agreed

## 1. 我々はなぜここにいるのか
- ★ YouTube をよく見る人が、手軽に遊べるゲームで暇をつぶし、友人と盛り上がれるようにする。
- 個人開発として、YouTube Data API v3 の利用と Cloud Run への公開を一通り経験する。
- 動画の人気がどのくらいかという感覚を、遊びながら試せるようにする。

（★は最も重要な理由）

## 2. エレベーターピッチ
暇な時間に手軽に遊びたい YouTube をよく見る人向けの、view-counter-game というブラウザで遊ぶ数字当てゲームである。これはワード選びで再生回数の大きさを読み合い、狙った数字に近づける駆け引きを楽しむことができ、一般的なクイズアプリや、YouTube をただ眺めることとは違って、サーバーが API から取得した最新の再生回数を正解に使うため、問題が古くならず、いつ遊んでも答えが変わるという特徴がある。

- ゲームの形式：検索ワードを選び、そのワードを含む動画の最大再生回数を使って、お題や目標の数字に近づける。

## 3. パッケージデザイン
- プロダクト名：view-counter-game（仮称）
- キャッチコピー：「その動画、何回再生された？」
- 利用者から見た価値
  1. 登録もインストールも不要で、ブラウザを開けばすぐ1ゲーム遊べる。
  2. 自分の「バズの感覚」がどれだけ当たっているかを、点数で確かめられる。
  3. 1台のスマホを回して、その場の友人と対戦できる。

## 4. やらないことリスト
### やる
- 検索ワード（スペース区切りで複数可）を入力すると、タイトルにすべてのワードを含む動画のうち、最も再生回数が多い動画の回数を使う。
- 3つのモードを作る。
  - カウントダウン：お題の数字から再生回数を引いていく。
  - チャージ：0から再生回数を足して目標に近づける。
  - ハイ＆ロー対戦：1台のスマホを回して遊ぶ。
- 同じワードの組み合わせは、1ゲームの中で2回使えないようにする。
- 条件に合う動画が検索結果の上位50件に無い場合は、そのプレイヤーをゲームオーバーにする。複数人で遊んでいる場合は、そのプレイヤーだけがゲームオーバーになる。
- 「同じワードの組み合わせ」は、語順の違い、大文字と小文字の違い、全角と半角の違いを同じとみなす。
- ハイ＆ロー対戦では、負けたプレイヤーは脱落し、残りのプレイヤーで続ける。最後の1人まで生き残ったプレイヤーか、0ちょうどになったプレイヤーが勝つ（試作版の「1人が負けた時点で対戦全体が終わる」から変える）。
- 難易度・ターン数・判定ロジック・見た目は、試作版のものをそのまま使う。
- サーバーで YouTube Data API v3 から再生回数を取得し、Cloud Run で公開する。
- スマホのブラウザで遊べるようにする。

### やらない
- ユーザ登録・ログイン
- サーバーに保存する全体ランキング
- 通信を使ったオンライン対戦（対戦は1台のスマホを回す形だけにする）
- スマホのネイティブアプリ

### 後で決める
- ルールの変更や、新しいルール・モードの追加
- 点数の共有方法（SNS 投稿ボタンを付けるか）

## 6. 技術的な解決策
### 技術スタック
- フロントエンド：React と TypeScript の SPA にする。ビルドには Vite を使う。試作版の見た目、判定ロジック、難易度、ターン数を React に移植する。
- バックエンド：Go で JSON API を作る。標準ライブラリの `net/http` を基本にする。
- 通信：フロントとバックは JSON の REST API だけでやり取りする。
- テスト：フロントは Vitest と React Testing Library を使う。バックは Go 標準の `testing` を使い、YouTube API の呼び出しはモックに差し替える。
- インフラ：Cloud Run にコンテナ1つで公開する。Go のサーバーが `/api/*` を処理し、ビルドした React の静的ファイルも配る。同じオリジンになるため、CORS の設定が要らない。

### 構成の概要
1. SPA が検索ワードを付けて `GET /api/views?q=...` を呼ぶ。
2. Go のサーバーが `search.list`（`order=viewCount`、最大50件）で動画を検索する。
3. タイトルにすべてのワードを含む動画だけを残す。
4. `videos.list` で再生回数を取得し、最大値を返す。条件に合う動画が無い場合は、その旨を返す。
5. 同じワードの結果は、サーバーのメモリに一定時間キャッシュする。
6. ゲームの進行（モード、得点、使用済みワード、ゲームオーバーの管理）はフロントで持つ。サーバーは再生回数を返すことだけを担う。

### 技術的な制約
- API キーはサーバーだけが持ち、ブラウザには渡さない。Secret Manager から環境変数で渡す。
- YouTube Data API の無料枠は1日10,000ユニットである。`search.list` は1回100ユニットかかるため、キャッシュしない場合は1日に約100回しか検索できない。
- 検索結果の上位50件だけを絞り込む。条件に合う動画が上位50件に無い場合は、そのプレイヤーをゲームオーバーにする（ルールとして扱う）。
- 自動テストは本物の YouTube Data API を呼ばない。API の呼び出しはインタフェースで切り離し、テストではモックや記録済みのレスポンスに差し替える。
- 本物の API を呼ぶのは、デモのリハーサルと PO の動作確認だけにする。手元の開発では、API キーが無いときにモックの結果を返す開発用モードを用意する。
- 試作版は https://claude.ai/artifact/Me713K9PQ8ijaxCZakN42g にある。1枚の HTML に素の JavaScript で書かれている。
  - 難易度は `LEVELS`（やさしい：6ターン・1億〜3億・許容5%、ふつう：5ターン・3億〜10億・許容2%、むずかしい：4ターン・10億〜50億・許容0.5%）で定義されている。
  - 再生回数の入力は「1.2億」「350万」「1,234,567」などを `parseViews` で読み取る。ワードの組み合わせは `normWords`（小文字化、半角・全角スペースで分割、並べ替え）で同一とみなす。
  - 試作版では、遊び手が YouTube を別タブで検索し、再生回数を手で入力する。本プロダクトでは、この手入力をサーバーによる自動取得に置き換える。

## 7. 夜も眠れない問題
| リスク | 影響 | 対策 | 兆候の見つけ方 |
|---|---|---|---|
| YouTube API のクォータを使い切る | その日は誰も遊べなくなる。 | 検索結果をキャッシュする。クォータ切れのときは「今日は遊べない」と画面に出す。 | API が `quotaExceeded` を返す。Google Cloud コンソールの利用量が上限に近づく。 |
| テストや開発中の動作確認でクォータを使い切る | 開発中に遊べなくなり、デモもできなくなる。 | 自動テストはモックだけを使う。本物の API はデモのリハーサルと PO の確認だけで呼ぶ。 | テストの実行後に、Google Cloud コンソールの利用量が増えている。 |
| 公開した API を第三者に連打される | クォータが枯れる。課金が増える。 | IP ごとの回数制限と、ワードの長さ制限を入れる。 | リクエスト数が急に増える。 |
| API キーが漏れる | 他人に使われ、クォータと課金を消費される。 | キーはサーバーだけが持つ。リポジトリに書かない。 | Google Cloud で見覚えの無い利用がある。 |
| 試作版の挙動を正しく移植できない | 遊び心地が試作版と変わる。 | 移植の前に試作版を受け取る。試作版の挙動をテストケースにする。 | レビューで PO が「試作版と違う」と指摘する。 |
| タイトルの一致判定がぶれる（大文字と小文字、全角と半角、表記ゆれ） | 遊び手が「入っているのにゲームオーバーになった」と不満を持つ。 | 正規化のルールを決めてテストする。 | 試遊で判定への苦情が出る。 |
| Cloud Run の課金が想定を超える | 個人の負担が増える。 | 予算アラートを設定する。最小インスタンス数を0にする。 | 予算アラートが届く。 |
| YouTube の利用規約に反する表示をする | API の利用を止められる。 | 動画の表示方法と出典の書き方を、公開前に規約と照らし合わせる。 | Google から警告が届く。 |

## 8. 期間を見極める
- 最初のリリースの目安：2026年11月末（4スプリント程度）。外部の締め切りではなく、自分で決めた目安とする。
- マイルストーン
  1. M1：手元で1モードが遊べる。Go の API が最大再生回数を返し、カウントダウンモードが手元のブラウザで最後まで遊べる。
  2. M2：3モードがそろう。チャージとハイ＆ロー対戦が加わり、ゲームオーバーと使用済みワードの判定が試作版どおりに動く。
  3. M3：Cloud Run で公開する。キャッシュ、回数制限、クォータ切れの表示、予算アラートを入れてから公開する。
- 最初のリリースに必要な最小の範囲：3モードすべてと、夜も眠れない問題のうちクォータ・連打・API キーへの対策。

## 9. トレードオフスライダー
1. 品質：試作版どおりのルールと遊び心地が、このゲームの価値そのものだからである。使いやすさ（スマホでの操作のしやすさ）も品質に含める。
2. 予算：個人開発で、API クォータと Cloud Run の課金を自分で負担するからである。
3. スコープ：最初のリリースは3モードと最低限の対策に絞ってあり、これ以上は削りにくいからである。
4. 時間：11月末は自分で決めた目安で、外部の締め切りではないからである。

- 期限が迫った場合：11月末に3モードがそろっていなければ、モードを削って公開するのではなく、公開日を延ばす。

## 10. 何がどれだけ必要か
- 期間：2026年11月末までの約4スプリント
- 費用
  - Agent の利用費：契約している Claude のプランの範囲内に収める。従量課金を追加しない。
  - Google Cloud：月1,000円を上限の目安とし、予算アラートを設定する。Cloud Run は最小インスタンス数を0にして、無料枠の範囲で動かす。
  - YouTube Data API：無料枠（1日10,000ユニット）の範囲だけで使う。クォータの増加は申請しない。テストやデモでクォータを使い切らないようにする（技術的な制約を参照）。
- 上限を超えそうなときの判断：PO が判断する。
- チーム編成
  - PO：ユーザ
  - スクラムマスター：メインセッション
  - Agent：フロントエンド実装（React）、バックエンド実装（Go）、UI デザイン、コードレビュー、セキュリティレビュー。具体的な Agent はチーム編成で提案し、PO の承認を得る。
  - 人間の関係者：友人（試遊者）
