# チーム合意

### T1-1: 実装前チェックリストを依頼に貼り、報告で答える
- なぜ（根本原因）: レビューで出た観点が、次の実装の依頼に渡る仕組みが無い。そのため、同じ型の指摘（ログの区別、タイムアウトの既定、panic 対策、設定の競合、テストの検証範囲、外部 API の仕様）が PBI をまたいで繰り返された。
- 誰が: スクラムマスター（依頼に貼る）と implement 枠（報告で答える）
- いつ: implement 枠に実装・差し戻しを依頼するたび
- どこで: implement 枠への依頼文と、implement 枠の報告の末尾
- 何を: 次のチェックリストを依頼文に貼り、implement 枠は各項目に「対応／該当なし（理由）」で答える。
  1. 外部 API を呼ぶ場合、使う各エンドポイントのパラメータを公式ドキュメントと突合し、「エンドポイント／パラメータ／根拠（ドキュメントの該当箇所）」の表を報告に付ける。併用不可・必須・上限の制約は、リクエストを記録する偽の HTTP サーバのテストで再現する。ドキュメントを参照できなければ unresolved に書く。
  2. goroutine を起こす処理は、panic を recover してエラーに変えるか、起こらない理由を書く。
  3. HTTP サーバとクライアントには明示的なタイムアウトを置く。nil 時の既定に `http.DefaultClient` を使わない。
  4. 矛盾した設定（例：開発用スイッチと本番の設定が同時にある）や不正な値は、警告ログか起動失敗にし、黙ってどちらかを選ばない。
  5. 上流エラー、呼び出し元のキャンセル、タイムアウトを、ログとステータスで区別できるようにする。
  6. 秘密情報がログに出ないことのテストは、実際のハンドラを通して検証する。
- どうやって: スクラムマスターは、直前のスプリントの should のうち同じ型に当たるものを、チェックリストの下に「前回の例」として添える。報告にチェックリストへの回答が無ければ、レビューに回す前に implement 枠へ追記を求める。
- 効果の確認: 次スプリントのレビューで、上の6項目に当たる should の件数を数える。Sprint 1 は 12 件（ログの区別 3、タイムアウトの既定 2、panic 2、設定の競合 1、テストの検証範囲 2、外部 API の仕様 1、その他の同型 1）。6 件以下なら効果ありとする。
- 行き先: チーム合意

### T1-2: レビュー依頼に既知の未対応リスクを付け、重大な疑いは must にする
- なぜ（根本原因）: レビュー依頼に「どのリスクをどの PBI で解消するか」が無く、レビュアーは既知の未対応と新しい穴を区別できなかった。また重要度の基準に「外部仕様との不一致の疑い」「プロセス全体が落ちる経路」の扱いが無く、should にすると追跡されなかった。
- 誰が: スクラムマスター（依頼文と追跡）と code-review 枠・security-review 枠（判定）
- いつ: code-review 枠・security-review 枠にレビューを依頼するたび
- どこで: レビュー依頼文の「既知の未対応リスク」節と、スプリントファイルの「記録」
- 何を: (1) 依頼文に「リスク｜解消する PBI｜状態」の表を付ける。元はデッキの「夜も眠れない問題」とバックログである。(2) レビュー枠は、表にあるリスクに当たる指摘を個別の should にせず、報告の末尾に「既知の未対応（#<PBI>）に該当：<ファイル:行>」と1行でまとめる。(3) 次の2つに当たる指摘は must とする。(a) 外部 API の公式仕様に反する疑いがあり、モックやテストでは確かめられない（根拠にドキュメントの該当箇所を書く）。(b) recover されない場所での panic など、1リクエストでプロセス全体が落ちうる経路がある。
- どうやって: 表の初期値は「連打・入力長の制限｜#7｜未着手」「クォータ切れの応答｜#10｜未着手」「クォータ切れの表示｜#11｜未着手」とする。スクラムマスターは、PBI の状態が変わるたびに表を更新する。
- 効果の確認: 次スプリントで、(1) 表にあるリスクが個別の should として出た件数が 0 件であること、(2) (a)(b) に当たる指摘が should のまま approve された件数が 0 件であること。両方を満たせば効果ありとする。
- 行き先: チーム合意
- Sprint 4 の改定: (2) は T2-2 (4)（should ごとに解消先を書く）と食い違っていた。表のリスクに当たる指摘は、should の行に「既知（#<PBI>）」とだけ書き、should の件数に数えない。表の列は T4-2 のとおり「残余リスク」を足す。

### T2-1: 画面に出る数字の表示規則を、PO の言葉と照合する
- なぜ（根本原因）: UI 仕様・実装・レビューのどの工程にも、「画面に出る数字ごとに、どう加工するか」と「その根拠になる PO の言葉（デッキ・受け入れ基準）」を照合する手順と材料が無い。そのため、受け入れ基準が触れていない数字（お題・目標・上限）は試作版のまま残った。根拠の無い判断（5.md「最初のお題は切り捨てずに比べる」）も通常の仮定に埋もれ、PO の確認に回らなかった。
- 誰が: スクラムマスター（依頼に材料を付ける）、design 枠（表を作る）、implement 枠（表に合わせる）、code-review 枠（照合する）
- いつ: 画面に数字を出す PBI の design・implement・review を依頼するたび
- どこで: design・implement・code-review への依頼文の冒頭、UI 仕様の「数字の表示規則」節、code-review の報告
- 何を: (1) スクラムマスターは、デッキと受け入れ基準のうち数字の扱いに関わる PO の言葉を、原文のまま依頼文の冒頭に引用する。(2) design 枠は、UI 仕様に「数字の表示規則」の表を付ける。(3) 根拠の列が空の行は、assumptions ではなく「PO に示す事項」に書く。(4) code-review 枠は、画面に出る数字をこの表と突き合わせる。表に無い数字や、PO の言葉に反する数字は must とする（受け入れ基準に書かれていなくても must とする）。
- どうやって: 表の列は「数字（例：お題、目標、上限、残り、合計、入力値）｜加工（切り捨て・丸め・桁区切り）｜根拠（デッキの文、または受け入れ基準の行）」とする。スクラムマスターは、根拠が空の行と、design 枠の「PO に示す事項」を、スプリントレビューで PO に示す。
- 効果の確認: 次に画面の数字を変える PBI があるスプリントで、次の3つを見る。(1) 「基準の書き漏れ」を区分とするデモの差し戻しが 0 件である。(2) 仮定の食い違い（PO が別の判断をした仮定）が 0 件である。(3) UI を含む PBI の仕様すべてに、表がある。3つとも満たせば効果ありとする。

### T2-3: 共通部品を定める PBI の UI 仕様を先に確定する
- なぜ（根本原因）: 共通部品を定める仕様（3.md）と、それに依存する仕様（4.md・5.md）を並列に書かせる計画だった。依存する側は、共通部品と横断の決定（数字の扱いなど）を想定で書いた。そのため、実装での読み替え、保守性の should（二重の結果画面、重複、グローバル CSS）、統合時の競合が生じた。
- 誰が: スクラムマスター（計画と依頼）、design 枠（突合を報告する）
- いつ: スプリント計画で、UI を含む PBI が複数あり、その一部が共通部品を定めるとき

- どうやって: 実行計画に「design の順序：<共通の PBI> → <残り>（並列）」と書く。共通の PBI の implement 依頼には、「後続の PBI が並列で足しても、共通ファイルの同じ行が競合しない登録の形にする」を入れる。

### T3-1: T1-1 の「対応」には根拠の表を付ける
- なぜ（根本原因）: T1-1 の回答が「対応／該当なし」の一語で、どの入力をどう扱い、どのテストで確かめたかが報告に残らない。項目4は「矛盾した設定」と「不正な値」の2つを1行に含む。そのため、#18 では矛盾だけを扱って「対応」と答えられた。assumptions（「1 以外はモック無効」）と回答が食い違っていても、レビューまで誰も気づかなかった。
- 誰が: スクラムマスター（依頼に書式を貼る、表の無い報告を差し戻す）、implement 枠（表で答える）、code-review 枠（表とテストを突き合わせる）

- どうやって: スクラムマスターは、T2-2 の「T1-1 の回答の有無」の確認と同じ箇所で、表の有無も確かめる。「対応」なのに表が無い報告は、レビューに回す前に追記を求める。レビュアーは、表の各行にテストがあるかを突き合わせる。

### T3-2: 実害のある指摘は、次のスプリント計画で必ず PO の判断を取る

- 誰が: スクラムマスター
- いつ: スプリント計画の最初の議題として
- どこで: T1-2 の既知リスクの表、スプリント計画で PO に示す内容
- 何を: (1) T1-2 の表に「PO の判断」の列を足す。(2) 次の2つに当たる指摘は、計画の最初の議題として PO に示し、優先度か「受け入れるリスク」かを決めてもらう。返答が無いまま計画を終えない。2つとは、実在の脆弱性（govulncheck などの検出）と、秘密の漏洩の経路である。(3) Sprint 4 の計画では、次の3つを PO に提案する。M3 の公開条件に「`make vuln` の検出が 0 件」を加えること。#13 の前提に #21 を加えること。DoD 変更案の採否。

- 行き先: チーム合意

### T3-3: 「不要」とした指摘には理由を書き、再レビューで前回の指摘の行方を書く
- なぜ（根本原因）: 解消先「不要」の should に、不要とする理由を書く規則が無い。再レビューの依頼にも、前回の should の一覧が無い。そのため、見送られた指摘の是非が記録上つながらない。
- 誰が: code-review 枠・security-review 枠（書く）、スクラムマスター（依頼に前回の一覧を入れる）
- いつ: すべてのレビュー。差し戻し後の再レビューの依頼
- どこで: レビューの報告の should の行、再レビューの依頼文、スプリントファイルの review の節
- 何を: (1) 解消先は「不要（理由）」と、理由を1文で書く。(2) 再レビューの依頼には、前回の must・should の一覧を入れる。(3) レビュアーは、前回の指摘の扱いを「対応／見送り（理由）／消滅」のどれかで1行ずつ書く。
- どうやって: スクラムマスターは、レビュー依頼の共通項目（判定のきまり）に、この2点を足す。
- 効果の確認: 次スプリントで、次の2つを見る。(1) 理由の無い「不要」が 0 件である。(2) 前回の指摘の扱いが書かれていない再レビューが 0 件である。両方を満たせば効果ありとする。
- 行き先: チーム合意

### T4-1: 受け入れ基準の原文を依頼に貼り、基準ごとの充足表で答える
- なぜ（根本原因）: 依頼には、基準そのものではなく、取得コマンドを書いていた。そのコマンドは、実行して本文が出ることを確かめていなかった。受け取った側にも、基準が無いときに止まる規則が無かった。報告の書式に基準ごとの欄も無いので、基準を読まなくても報告や判定が書けた。そのため、#7 の code-review、#21 の security-review、#10 と #22 の implement が本文を読まずに進んだ。#10 では、基準2と食い違う仮定（`dailyLimitExceeded` を 503 にする）が must になった。
- 誰が: スクラムマスター（依頼に原文を貼る、表の無い報告を差し戻す）、implement 枠（表で答える、基準と食い違う仮定を置かない）、code-review 枠・security-review 枠（表で判定する、基準が無ければ止まる）
- いつ: implement 枠とレビュー枠に、実装・差し戻し・レビュー・再レビューを依頼するたび
- どこで: 依頼文の冒頭の「受け入れ基準（原文、N 項目）」の節、各枠の報告の冒頭
- 何を: (1) スクラムマスターは、`gh issue view <番号> --json body` の出力から、受け入れ基準を原文のまま依頼に貼り、項目数 N を書く。取得コマンドを依頼に書くだけで済ませない。(2) 各枠は、報告の冒頭に「基準｜充足（対応／未対応）｜根拠のテスト名」の表を、N 行で書く。(3) 依頼に基準の原文が無いとき、または行数が N と合わないときは、実装も判定もせず `blocked`（入力不足）で返す。(4) implement 枠は、基準に書かれた挙動（ステータス、コード、値の集合）と食い違う仮定を置かない。食い違う方が妥当に見えても、基準どおりに実装し、提案を unresolved に書く。assumptions の各行には「基準との関係：第<n>項／該当なし」を付ける。
- どうやって: スクラムマスターは、雛形を変えたときに取得コマンドを1回実行し、本文が出ることを確かめてから使う。報告を受け取ったら、表の行数が N と合うかを、T2-2・T3-1 と同じ確認の箇所で見る。合わなければ、次の工程に回す前に追記を求める。
- 効果の確認: 次スプリントで、次の3つを見る。(1) 基準を読まずに出た実装・判定が 0 件である。(2) 表の行数が N と合わないまま次の工程に回った報告が 0 件である。(3) 基準と食い違う仮定による must が 0 件である。3つとも満たせば効果ありとする。

### T4-2: リスクを閉じる量的な条件を確かめ、既知リスクの表に残余リスクを書く
- なぜ（根本原因）: デッキのリスクの対策を受け入れ基準に写すときに、「そのリスクを防げた」と言える量的な条件を確かめる手順が無い。例えば、全体で1日に何ユニットまでに収まるか、という条件である。T1-2 の表は、リスクと PBI を1対1で結び、PBI が終わった後に残る穴を書く列が無い。そのため、#7 の IP ごとの制限ではクォータ切れを防げないことに、レビューの段階まで気づかなかった（#26）。
- 誰が: スクラムマスター（依頼と表の更新）、security-review 枠（リファインメントで量を計算する）
- いつ: デッキの「夜も眠れない問題」に関わる PBI の、リファインメントの見積り。レビュー依頼の直前の、表の更新
- どこで: リファインメントの見積りの依頼と記録、T1-2 の既知リスクの表、PBI の受け入れ基準への追記案
- 何を: (1) 夜も眠れない問題に関わる PBI のリファインメントでは、implement 枠の見積りと並べて security-review 枠を「見積りのみ」で起動する。security-review 枠は、デッキの技術的な制約から、攻撃者1人あたりの最大消費と、全体の上限を計算して示す。(2) 計算で収まらなければ、基準の不足として PO に示す。PO に示すときは、基準の追記案か、別の PBI の案を付ける。(3) T1-2 の表に「残余リスク」の列を足し、PBI が完了した後も残る穴と、その解消先を書く。
- どうやって: 表の列は「リスク｜解消する PBI｜状態｜PO の判断｜残余リスク」とする。Sprint 4 の時点の残余リスクは次の4行である。連打は「全体の上限なし｜#26」。回数制限は「満杯時の走査・ログ量・プロキシの前提｜#27」。依存は「x/text の module レベルの検出｜#28」。画面は「429 の表示なし｜#25」。
- 効果の確認: 次スプリントで、次の2つを見る。(1) デッキのリスクに関わる PBI について、「その PBI ではリスクを防げない」とレビューで初めて指摘された件数が 0 件である。(2) 表の「残余リスク」が空の行が 0 件である。どちらも満たせば効果ありとする。
