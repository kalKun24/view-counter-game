# plugin への改善提案

## Sprint 1
- 対象：`code-reviewing` と `security-reviewing` の判定書式
- 事象：環境の都合で実行できなかった検証（`-race`、`govulncheck`）を、判定書式で表す欄が無い。報告の末尾に毎回書かれるだけで、対処の対象にならなかった。
- 提案：`checks`（または `tests`）欄を「実行：<コマンドと結果>」「未実行：<コマンド>／理由」の2行構成にする。`sprint-execution` で、未実行が複数の PBI で続いたら改善 PBI の候補として記録する手順を足す。
- 事象：重要度の基準に「外部仕様に反する疑い（モックでは確かめられない）」「プロセス全体が落ちる経路」の扱いが無く、どちらも should として承認された。
- 提案：must の例に、この2つを加える。今回はチーム合意 T1-2 で先に試す。

## Sprint 2
- 対象：`ui-designing` の出力書式
- 事象：画面に出る数字ごとの加工（切り捨て・丸め）と、その根拠を書く節が無い。「受け入れ基準との対応」は基準から要素への一方向だけで、基準に根拠の無い表示や仮定が洗い出されなかった。その結果、デモが差し戻された（お題の端数）。
- 提案：「数字の表示規則」の節（数字｜加工｜根拠）を足す。対応表に、要素から基準への逆向きの確認を足す。根拠の無い行は「PO に示す事項」に出す。今回はチーム合意 T2-1 で先に試す。
- 対象：`code-reviewing` の観点
- 事象：観点が受け入れ基準と UI 仕様に限られる。PO の言葉（デッキ）に反するが基準に書かれていない振る舞いを、レビューで拾えない。
- 提案：依頼にデッキの該当する記述を付けることと、それに反する振る舞いを must（基準の書き漏れ）とすることを、観点に足す。
- 対象：`frontend-implementing`（と `backend-implementing`）
- 事象：手動確認のために起動した開発サーバが、報告の後も残った。
- 提案：「起動したプロセスは報告の前に止め、残りが無いことを報告に書く」を基準に足す。
- 対象：`security-reviewing` と `invisible-characters`
- 事象：不可視文字の Grep が、ロケールの違いで検出できているかどうか分からなかった。
- 提案：既知の不可視文字を書いた一時ファイルで、同じパターンが検出することを先に確かめる手順（陽性対照）を足す。
- 対象：`sprint-demo`（見せ直し）
- 事象：統合ブランチを作り直すとき、無視されたファイル（`web/.vite`）がディレクトリに残っていた。そのため `git worktree add` が失敗し、ブランチだけが作られた。また、1回目と同じ競合を、もう一度最初から解消した。
- 提案：作り直しの手順に、ディレクトリが残っていないことの確認を足す。競合の解消を再利用する手段（`git rerere`、または前の回の解消コミットの参照）を足す。

## Sprint 3
- 対象：`scrum-protocol` の implement の報告書式
- 事象：チェックリストへの回答が「対応／該当なし」の一語で、根拠（扱う入力の一覧、対応するテスト名）が残らない。複合した項目（「矛盾した設定」と「不正な値」）に、片方だけを扱って「対応」と答えられた（#18 の must）。
- 提案：「対応」と答えた項目に、入力の一覧とテスト名を添える書式にする。今回はチーム合意 T3-1 で先に試す。
- 対象：`security-reviewing` と `invisible-characters`（Sprint 2 の提案の再掲）
- 事象：不可視文字を扱わないと判断した PBI では、Grep が実行されなかった。陽性対照の手順も、まだ無い。
- 提案：Grep を全 PBI で必須にし、件数と陽性対照の結果を checks に書く。
- 対象：`run-sprint`（スクラムマスターの記録の書き方）
- 事象：記録の追記に `python3 -c "..."` を使い、二重引用符の中のバッククォートがシェルに展開されて、意図しないコマンドが実行された。
- 提案：記録の追記は Write／Edit か、単一引用符のヒアドキュメントで行うことを、原則の「Bash は1回に1コマンド」の近くに明記する。

## Sprint 4
- 対象：`scrum-protocol`（全枠の手順）と `code-reviewing`・`security-reviewing` の判定書式
- 事象：依頼に PBI の取得コマンド（`gh issue view <番号> --comments`）だけを書き、本文が届かなかった。それでも実装と判定が成立した（#7・#10・#21・#22）。#10 では、基準と食い違う仮定が must になった。
- 提案：各枠の手順に「受け入れ基準の原文が無い・項目数が合わないときは `blocked`（入力不足）」を足す。判定書式と implement の報告に「基準｜充足｜根拠のテスト名」の表を足す。implement の仮定の規則に「基準に書かれた挙動と食い違う仮定は置かない」を足す。今回はチーム合意 T4-1 で先に試す。
- 対象：`backlog-operations` の `github.md`（`get` の手順）
- 事象：`gh issue view --comments` は本文を表示しない。スクラムマスターが依頼の雛形に使い、誰も気づかなかった。
- 提案：`get` の手順に `gh issue view <番号> --json title,body,labels,comments` を明記し、`--comments` は本文を出さないと注記する。
- 対象：`sprint-demo` の `format.md`
- 事象：デモスクリプトの起動確認が `/api/views` を叩き、回数制限の1回を使った。リハーサルの初回が不一致になった。
- 提案：起動確認と準備の操作は、状態（回数制限・キャッシュ・一度きりの状態）を消費しないパスで行うことを書式に足す。
- 対象：`ui-designing` の出力書式
- 事象：UI 仕様が「429 は #7 で扱う」と仮定したが、#7 は `ui: no` で、画面の担当が無かった（#25）。「PO に示す事項」は、案のまま実装されてから PO に示された。
- 提案：(1) 「扱う応答の一覧（応答コード｜画面の表示｜担当 PBI）」の節を足し、担当が `ui: no` の PBI なら「PO に示す事項」に載せる。(2) 「PO に示す事項」に「別案｜案を変えたときの変更範囲｜基準の文言と合うか」を足す。
- 対象：`frontend-implementing` の「テスト」
- 事象：取得中に「やめる」を押すテストが、`await Promise.resolve()` 1回の待機で無意味に通る可能性がある（#11 の code-review）。
- 提案：否定の assertion は、応答の処理が済んだことを示す別の事象を待ってから書く。一度実装を壊して fail することを確かめ、報告に書く。
