# plugin への改善提案

## Sprint 1
- 対象：`code-reviewing` と `security-reviewing` の判定書式
- 事象：環境の都合で実行できなかった検証（`-race`、`govulncheck`）を、判定書式で表す欄が無い。報告の末尾に毎回書かれるだけで、対処の対象にならなかった。
- 提案：`checks`（または `tests`）欄を「実行：<コマンドと結果>」「未実行：<コマンド>／理由」の2行構成にする。`sprint-execution` で、未実行が複数の PBI で続いたら改善 PBI の候補として記録する手順を足す。
- 事象：重要度の基準に「外部仕様に反する疑い（モックでは確かめられない）」「プロセス全体が落ちる経路」の扱いが無く、どちらも should として承認された。
- 提案：must の例に、この2つを加える。今回はチーム合意 T1-2 で先に試す。

## Sprint 2
- 対象：`ui-designing` の出力書式
- 事象：画面に出る数字ごとの加工（切り捨て・丸め）と、その根拠を書く節が無い。「受け入れ基準との対応」は基準から要素への一方向だけで、基準に根拠の無い表示や仮定が洗い出されなかった。その結果、デモが差し戻された（お題の端数）。
- 提案：「数字の表示規則」の節（数字｜加工｜根拠）を足す。対応表に、要素から基準への逆向きの確認を足す。根拠の無い行は「PO に示す事項」に出す。今回はチーム合意 T2-1 で先に試す。
- 対象：`code-reviewing` の観点
- 事象：観点が受け入れ基準と UI 仕様に限られる。PO の言葉（デッキ）に反するが基準に書かれていない振る舞いを、レビューで拾えない。
- 提案：依頼にデッキの該当する記述を付けることと、それに反する振る舞いを must（基準の書き漏れ）とすることを、観点に足す。
- 対象：`frontend-implementing`（と `backend-implementing`）
- 事象：手動確認のために起動した開発サーバが、報告の後も残った。
- 提案：「起動したプロセスは報告の前に止め、残りが無いことを報告に書く」を基準に足す。
- 対象：`security-reviewing` と `invisible-characters`
- 事象：不可視文字の Grep が、ロケールの違いで検出できているかどうか分からなかった。
- 提案：既知の不可視文字を書いた一時ファイルで、同じパターンが検出することを先に確かめる手順（陽性対照）を足す。
- 対象：`sprint-demo`（見せ直し）
- 事象：統合ブランチを作り直すとき、無視されたファイル（`web/.vite`）がディレクトリに残っていた。そのため `git worktree add` が失敗し、ブランチだけが作られた。また、1回目と同じ競合を、もう一度最初から解消した。
- 提案：作り直しの手順に、ディレクトリが残っていないことの確認を足す。競合の解消を再利用する手段（`git rerere`、または前の回の解消コミットの参照）を足す。
