# 25 UI 仕様

PBI #25「連打の制限（429）の表示（画面）」。共通部品は #3 の仕様（`.scrum/designs/3.md`）、並びの先例は #11 の仕様（`.scrum/designs/11.md`）に任せる。この仕様は「429 かつ `too_many_requests`」の状態の差分だけを定める。3モード（カウントダウン、チャージ、ハイ＆ロー対戦）は同じ共通の SearchForm を使うため、表示は SearchForm と FetchStatus で1か所に定め、各モードは改造しない。

## 前提（サーバの応答）
サーバの契約は #7 で決まっている。この仕様は PBI #25 の受け入れ基準を前提にする。

- 画面側の判定：ステータスが `429` かつ本文の `error.code === "too_many_requests"` のときだけ「制限中」とする。
- 待ち秒数は、応答ヘッダー `Retry-After` から読む。同一オリジンのため、ヘッダーは読める。
- 上記以外の `429`（本文が読めない、`code` が別の値、`code` が無い）は、これまでどおり「通信失敗」（#3 の仕様の取得結果の分類）として扱い、再試行ボタンを出す（基準5）。
- 判定の順序：`429` の確認は `503`（クォータ切れ）と独立している。両者は混ざらない。

## 対象画面・コンポーネント
既存の変更。新規の画面も、新規の部品も作らない（既存の `.msg` を使い、新しい色・余白・CSS を足さない）。

| 対象 | 変更 |
|---|---|
| `web/src/api/views.ts` | `ViewsResult` に `{ kind: "throttled"; retryAfter: number \| null }` を足す。`classify` で `429` かつ `too_many_requests` のとき返す。`Retry-After` の読み方は「数字の表示規則」のとおり。`429` で本文が読めない、または `code` が別の値なら、従来の `{ kind: "error", reason: "http", status: 429 }`。 |
| `web/src/hooks/useViewsFetch.ts` | `FetchState` に `{ kind: "throttled"; retryAfter: number \| null }` を足す。`throttled` のときは `onResult` を呼ばず、使用済みにも追加しない（`invalid` と同じ扱い）。ログは `console.warn("views fetch rejected: too_many_requests")` の1行（`Retry-After` の値は含めてよい。検索ワードは含めない）。 |
| `web/src/components/FetchStatus.tsx` | `state.kind === "throttled"` のとき、role=status の領域に `.msg` の `<p>` を1つ出す。再試行ボタンは出さない。`data-state="throttled"`。 |
| `web/src/components/SearchForm.tsx` | 「重複・通信失敗・q 不正のあと」のフォーカス戻しの対象に `throttled` を足す。それ以外は変えない。panel の入れ替えはしない（`QuotaNotice` のような分岐を足さない）。 |
| 各モード（CountdownPlay、ChargePlay、VersusPlay） | 変更なし。`onResult` が呼ばれないため、判定、履歴、使用済みワード、結果画面には触れない。 |

## 構成
プレイ画面の構成は #3 のまま変えない。検索フォームの panel を残し、その中の FetchStatus に文言を足すだけにする。

```
ScreenTop［やめる］［モード名（h1）］        ← そのまま
（モードごとの表示）                         ← そのまま
  カウントダウン：Counter（残り・残りターン）
  チャージ：チャージのカウンター（合計・あと何回・バー）
  ハイ＆ロー対戦：のこり N 人 / 全 M 人、生存者一覧、Counter（直前の判定値、手番のプレイヤー）
panel（SearchForm。form 要素。そのまま）
  label「検索ワード（スペース区切りで複数可）」
  input（入力は残る）
  button.btn「決定」（押せる）
  FetchStatus（data-state="throttled"）
    role=status の領域の中に p.msg（制限の文言）   ← 追加
panel「履歴」（WordLog。そのまま）
```

- 結果画面（`ResultBanner`）にも、引き継ぎカード（ハイ＆ロー対戦）にも遷移しない。
- 「もう一度試す」（`retry-button`）は出さない。通信失敗の文言（`error-message`）も出さない（基準3）。
- 文言は `.msg`（太字、通常色）にする。`.msg.bad`（赤）は使わない。失敗ではなく「待てば遊べる」状態のため、通信失敗・q 不正・重複の赤と見た目でも区別する。文言そのものでも区別できる（色だけに頼らない）。
- 文言の位置は、他のメッセージ（重複・q 不正）と同じ FetchStatus の位置。レイアウトは動かさない。

## 状態
#3 の仕様の「検索フォーム（プレイ中）」の状態表に、次の行を足す。

| 状態 | data-state | 入力 | 決定ボタン | FetchStatus の表示 | 遷移条件 |
|---|---|---|---|---|---|
| 制限中 | throttled | 入力を保持（編集可） | 有効（入力が空でなければ。空なら #3 どおり無効） | 「操作が多すぎます。あと約N秒待ってから、もう一度試してください。」。N が出せないときは「少し待ってから、もう一度試してください。」。`.msg`、再試行ボタンなし | 取得中に `429` かつ `too_many_requests` を受けた |

- 検索ワードは消さない（基準3）。`found` のときだけ入力を空にする既存の処理のままで、`throttled` では空にしない。
- 時間が経っても自動では消えない。カウントダウンはしない（基準2）。N は応答を受けた時点の値のまま動かない。
- 消えるとき：入力を変えたとき（`dismiss`）、または次の送信を始めたとき（取得中へ移る）。#3 の「重複・通信失敗・q 不正」と同じ規則。
- 決定ボタンを押すと、事前チェック（重複）を通って再び API を呼ぶ。制限中でも送信を禁じない（基準3）。再び 429 なら、新しい N で同じ状態になる。
- この状態は画面側に記憶しない。リロードやホームへ戻ったあとは、新しくゲームを始めて検索したとき、まだ制限中なら同じ表示になる。

### モードごとの扱い
| モード | 制限中のときの表示 | ゲームの状態 |
|---|---|---|
| カウントダウン | 検索フォームの下に文言。Counter は直前の残りと残りターンのまま。 | 残り、履歴、使用済みワード、ターンを変えない。`GAME OVER` にも `CLEAR` にもしない。 |
| チャージ | 同上。合計、あと何回、バー、残りターンは直前のまま。 | 合計、履歴、使用済みワード、ターンを変えない。バーストやターン切れの判定もしない。結果画面へ行かない。 |
| ハイ＆ロー対戦 | 同上。生存者一覧、手番の表示、直前の判定値は直前のまま。引き継ぎカードは出さない。 | 当該プレイヤーを脱落させない。手番を動かさず、生存者数、前の値、履歴、使用済みワードを変えない。結果画面（`GAME SET`）にも勝者にも遷移しない。同じプレイヤーが待ったあとで検索を続ける。 |

- ハイ＆ロー対戦で脱落扱いにしない理由：#11 と同じ。429 はサーバ側の都合で、プレイヤーの手とは関係がない（基準4）。

## 数字の表示規則（T2-1）
| 数字 | 加工 | 根拠 |
|---|---|---|
| 待ち秒数 | サーバ値の整数秒をそのまま、端数・桁区切りなし、欠落・不正なら出さない | 基準2（Sprint 5 のリファインメントで PO が承認） |
| 上記以外の数字（お題、残り、合計、上限、目標、判定値、履歴の切り捨て値と実際の再生回数） | 変えない。#3・#4・#5 の表示規則のまま。429 の表示はこれらを変更も再計算もしない | 基準4（ゲームの状態を変えない）。PO の言葉（「10,000未満は切り捨て…正しい数字も注釈で出しておく」）に反する数字は、この仕様に無い |

`Retry-After` の読み方（待ち秒数の「欠落・不正」の定義）

| `Retry-After` の値 | 表示 |
|---|---|
| 半角数字だけの文字列（前後の空白は除く）で、1以上の安全な整数（例：`30`、`7`） | 「あと約N秒」。N はその整数（先頭の 0 は除いて `Number` にした値。例：`007` は 7） |
| ヘッダーが無い | 秒数を出さない文言 |
| `0`、負の値（`-5`）、空文字 | 同上 |
| 数字でない（`abc`、日時形式 `Wed, 21 Oct 2026 07:28:00 GMT`） | 同上 |
| 小数（`1.5`）、符号付き（`+5`）、桁区切り（`1,000`）、単位付き（`30s`） | 同上（整数秒の形でないため不正とみなす） |
| `Number.MAX_SAFE_INTEGER` を超える数字 | 同上（正確な整数として扱えないため不正とみなす） |

- 端数を丸めない（切り上げも切り捨てもしない）。`1.5` を `2` にしない。
- 桁区切りを付けない（`comma` を使わない）。`3600` は「約3600秒」。「約1時間」「1分」への言い換えもしない。上限も設けない。
- 「約」は基準1の文言の一部で、N が正確な待ち時間ではない目安であることを示す。N を増減しない。

## 扱う応答の一覧
`GET /api/views?q=` の応答ごとの画面の表示。

| 応答コード | 画面の表示 | 担当 PBI |
|---|---|---|
| 200 `found: true` | 判定へ進む（モードごと。使用済みに追加、履歴に追加）。 | #3・#4・#5 |
| 200 `found: false`（該当なし） | GAME OVER、または対戦では当該プレイヤーの脱落（モードごと）。 | #3・#4・#5 |
| 400 `invalid_query` | 「このワードでは検索できません。別のワードを入れてください。」（`data-state="invalid"`、再試行なし）。 | #3 |
| 429 `too_many_requests` ＋ `Retry-After` | この仕様の「制限中」（`data-state="throttled"`）。通信失敗とは別の表示。再試行なし。ゲームの状態は変えない。 | #25（サーバの契約は #7） |
| 429 で `code` が `too_many_requests` 以外、または本文が読めない | 従来の通信失敗（「取得に失敗しました。…」と「もう一度試す」）。 | #3（基準5） |
| 499 `canceled` | クライアントに届かない。画面側は、やめる・画面遷移で自分が中止した場合を `cancelled` として結果を捨てる（表示なし）。 | #3 |
| 502 `upstream_error` | 通信失敗（「取得に失敗しました。…」と「もう一度試す」）。ターンは減らない。 | #3 |
| 503 `quota_exceeded` | 「今日は遊べません」（QuotaNotice。panel を入れ替え、「ホームへ戻る」だけ）。 | #11（サーバは #10、上限到達は #26） |
| 503 で `code` が `quota_exceeded` 以外 | 従来の通信失敗。 | #3 |
| 504 `timeout` | 通信失敗（5xx）。クライアント側の15秒のタイムアウトも同じ。 | #3 |

担当が `ui: no` の PBI（#7、#10、#26）に関わる行（429 のサーバ契約、503 の上流・上限到達）は、画面の表示の担当を #25・#11 にしている。#26 の扱いは「PO に示す事項」1 を参照。

## 操作
| 操作 | 結果 | 失敗時の表示 |
|---|---|---|
| 検索ワードを入れて決定し、`429` と `too_many_requests` を受ける | 状態「制限中」へ。FetchStatus に文言を出す。入力は残す。フォーカスを検索入力へ戻す。`onResult` を呼ばない。 | なし |
| 制限中に入力を変える | 文言を消す（`idle`）。 | なし |
| 制限中に決定を押す、または入力欄で Enter | 取得中へ移り（文言を消す）、API を呼び直す。 | 再び 429 なら新しい N で制限中。ほかは各行のとおり。 |
| 制限中に「やめる」（ScreenTop）を押す | ホームへ（#3 のまま）。ゲームの状態は破棄する。 | なし |
| 取得中に「やめる」を押す | リクエストを中止し、結果を捨てる（#3 のまま）。429 が届いていても表示しない。 | なし |
| 再試行 | 操作が存在しない（ボタンを出さない）。 | なし |

## 文言
- 秒数があるとき：操作が多すぎます。あと約N秒待ってから、もう一度試してください。（N は半角数字。例：「あと約30秒」）
- 秒数が出せないとき：少し待ってから、もう一度試してください。
- 補足の文言（「ターンは減っていません」など）は足さない。基準が文言を定めているため。
- 「エラー」「失敗」「通信」「取得に失敗」の語を使わない（通信失敗の文言と区別するため）。
- 「秒」は N の直後に付ける（「30 秒」と空けない）。「あと約」「秒」の前後に空白を入れない。

## アクセシビリティ
- フォーカス：制限中になったら、フォーカスを検索入力へ戻す（重複・q 不正のあとと同じ。入力が残るため、すぐ編集・再送できる）。panel を入れ替えないため、見出しへの移動はしない。
- 読み上げ：文言は FetchStatus の `role="status"`（`aria-live="polite"`）の領域に出すので読み上げられる。`role="alert"` にしない（通信失敗の扱いと区別するため、また即座に割り込む必要がないため）。重ねて別の live 領域を足さない。
- 同じ N で再び 429 を受けた場合：文言が変わらないと読み上げが繰り返されない。ただし再送の前に「取得中…」を経由して文言が一度消えるため、再度読み上げられる。
- キーボード：決定は `<button type="submit">`、Enter で送信。タブ順は #3 のまま（やめる、検索入力、決定）。新しく押せる要素は無い。
- 色：新しい色を使わず、`.msg` の既存トークンのまま。コントラストは #3 の仕様のとおり。状態は文言で伝える。
- タッチ：決定は高さ44px以上（#3 のまま）。
- 動き：アニメーションを足さない。
- 360px 幅：文言は折り返す。固定幅を置かない。横スクロールを出さない。最長でも数行の文言のため、`overflow-wrap:anywhere` は要らない（既存の `.msg` のまま）。

## 仮定
- 応答の形（`429`、`error.code` が `too_many_requests`、`Retry-After`）は #7 の基準どおり。#26 が既定の回数制限を 1分10回に下げるため、通常の待ちは1分以内になる想定だが、画面側は N に上限を設けない。
- 補足の1行（「ゲームは進んでいません」など）は足さない。基準1が文言を定めているため。基準4（ゲームの状態を変えない）は、画面が変わらないことで確かめられる。
- `Retry-After` の「数字」は、HTTP の delay-seconds（半角数字のみ）に限る。日時形式は不正とみなして秒数を出さない（基準2の「数字でないとき」に当たる）。`Number.MAX_SAFE_INTEGER` を超える値は不正とみなす。この2点は基準に書かれていない境界の扱いで、基準の文言（整数秒をそのまま、数字でないときは出さない）の範囲で決めた。
- 制限中の文言の色は `.msg`（通常色）にして `.msg.bad` を使わない。基準は色を定めていない。通信失敗との区別を、文言と色の両方で付けるため。
- 文言を消す条件は、#3 の「重複・通信失敗・q 不正」と同じ（入力を変えたとき、または次の送信を始めたとき）。基準に消す条件の記載は無い。
- 制限中でも決定ボタンを押せるため、遊び手が待たずに押し続けられる。それを止める仕組み（一時的な無効化）は、基準3に反するので作らない。
- 429 のログ出力はフロントの `console.warn` を1行だけ置く（`invalid_query` と同じ程度）。検索ワードを含めない。

## PO に示す事項
基準と合わない事項は作らない。以下は基準の範囲内で、根拠が基準にない判断である。

1. 503 `quota_exceeded` の上限到達（#26、`ui: no`）の文言。#26 は、自前の1日の上限に達したときと、上流が 403 `quotaExceeded` を返したあとの1時間の抑制のとき、どちらも 503 `quota_exceeded` を返す。#11 の QuotaNotice の文言は「サーバーの1日の利用上限に達しました。日をあらためて、もう一度遊んでください。」で、1時間の抑制には「日をあらためて」が合わない。1時間後に再開するため、遊び手が1日待ってしまうおそれがある。
   - 案：今の #11 の文言のまま変えない（#26 の基準は応答コードを変えないため、画面は区別できない。1日の上限が主な原因として扱う）。
   - 別案：「しばらく、または日をあらためて、もう一度遊んでください。」のように、待ち時間を限定しない文言にする。
   - 案を変えたときの変更範囲：`QuotaNotice.tsx` の文言1文、`designs/11.md` の文言、#11 の文言を確かめるテスト。応答の区別はしない（サーバの契約変更は要らない）。区別して出し分ける場合は、サーバが別の `error.code` を返す必要があり、#26 の基準の変更になる。
   - 基準の文言と合うか：#25 の基準とは無関係（#11 の基準「今日は遊べない旨を表示する」の範囲内で、どちらの文言も合う）。
2. 429 の表示に、補足の1行（「ターンは減っていません。」）を付けるか。#3 の通信失敗と #11 の QuotaNotice には付いている。
   - 案：付けない（基準1が文言を定めているため）。
   - 別案：基準の文言の下に `.muted.small` で「ターンは減っていません。」を付ける。
   - 案を変えたときの変更範囲：`FetchStatus.tsx` に `<p>` を1つと、testid（例 `throttle-note`）、この仕様の「文言」。
   - 基準の文言と合うか：案は合う。別案は、基準1の文言に1行足すので、PO が許す場合に限る（基準4の趣旨とは合う）。
