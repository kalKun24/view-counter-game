# 32 UI 仕様

PBI #32「上限・抑制中の待ち時間を伝える（Retry-After と画面の文言）」。画面側は、#11 の QuotaNotice（クォータ切れの表示）の見出しと文言を変え、503 の `Retry-After` から待ち時間を出す。サーバ側（基準1〜5）は別の担当で、画面は値を受けるだけである。共通部品は #3 の仕様（`.scrum/designs/3.md`）、元の仕様は #11（`.scrum/designs/11.md`）、並びの先例は #25（`.scrum/designs/25.md`）に任せる。この仕様は差分だけを定める。

#11 の「見出し」「説明」の文言と、#25 の「PO に示す事項」1 は、この仕様が置き換える。11.md と 25.md のそれ以外の記述（構成、モードごとの扱い、操作、フォーカス）は変えない。

## 状態
#11 の状態「クォータ切れ」（`data-state="quota"`）を、待ち時間の有無で2つの表示に分ける。状態の名前と遷移条件は変えない。

| 状態 | 表示 | 遷移条件 |
|---|---|---|
| クォータ切れ（待ち時間あり） | h2「いまは遊べません」、説明「サーバーの利用上限に達しました。あと約N<単位>で、もう一度遊べます。」、注記、「ホームへ戻る」 | 取得中に 503 かつ `quota_exceeded` を受け、`Retry-After` が使える。 |
| クォータ切れ（待ち時間なし） | h2「いまは遊べません」、説明「サーバーの利用上限に達しました。しばらくしてから、もう一度遊んでください。」、注記、「ホームへ戻る」 | 取得中に 503 かつ `quota_exceeded` を受け、`Retry-After` が使えない。 |

- 待ち時間は応答を受けた時点の値のまま動かない。時間が経っても自動で更新も消去もしない。カウントダウンはしない。
- 検索を再開する操作は無い（11.md のまま）。ホームへ戻って新しく検索して、まだ切れていれば、その時点の新しい値で同じ表示になる。回復していれば通常どおり遊べる。
- この状態を画面側に記憶しない（11.md のまま）。受けた `Retry-After` を保存して、再訪時の残り時間を計算することもしない。
- モードごとの扱い（ゲームの状態を変えない、脱落にしない、など）は 11.md の表のまま。待ち時間の有無で変わらない。

## `Retry-After` の読み方
「使える `Retry-After`」とは、`parseRetryAfter`（`web/src/api/views.ts`）が `null` 以外を返す値である。この関数は 25.md（429）で定めた規則そのままで、503 でも同じ関数を使い、規則を変えない。基準4（サーバは1以上の整数秒を返す）と一致する。

| `Retry-After` の値 | 使えるか | 扱い |
|---|---|---|
| 半角数字だけの文字列（前後の空白は除く）で、1以上の安全な整数（例：`3600`、`59`、`0060`） | 使える | その整数を秒として、「変換規則」で文字にする。先頭の 0 は除く（`0060` は 60）。 |
| ヘッダーが無い | 使えない | 「しばらくしてから」の文。 |
| 空文字、`0`、負の値（`-5`） | 使えない | 同上。 |
| 数字でない（`abc`） | 使えない | 同上。 |
| HTTP 日付形式（`Wed, 21 Oct 2026 07:28:00 GMT`） | 使えない | 同上。端末の時計で残りを計算しない（時計のずれで誤った待ち時間を出さないため）。基準4は整数秒と定めているので、日付形式は想定外の値である。 |
| 小数（`1.5`）、符号付き（`+5`）、桁区切り（`1,000`）、単位付き（`30s`） | 使えない | 同上。画面側で丸めて使うことはしない（端数の切り上げはサーバの責務）。 |
| `Number.MAX_SAFE_INTEGER` を超える数字 | 使えない | 同上。 |
| 複数の値が並ぶもの（`60, 60`） | 使えない | 同上（半角数字だけではないため）。 |

- 503 で `quota_exceeded` 以外の場合、`Retry-After` が付いていても読まない。従来の通信失敗（「もう一度試す」あり）のままにする。
- 200、400、502、504 などの `Retry-After` は読まない。
- 使えない値が来ても、画面を壊さず、エラー表示にもしない（「待ち時間なし」の文を出す）。`console.warn` の `retryAfter` は `null` になる。

## 変換規則
使える秒数 `s`（1以上の整数）を、次の規則で「約N<単位>」にする。判定は切り上げ前の `s` で行う。

| `s` の範囲 | 単位 | N | 例 |
|---|---|---|---|
| 1以上 60未満 | 秒 | `s` | 59 → 約59秒 |
| 60以上 3600未満 | 分 | `ceil(s / 60)` | 61 → 約2分 |
| 3600以上 | 時間 | `ceil(s / 3600)` | 3601 → 約2時間 |

- 端数は常に切り上げる（切り捨て・四捨五入にしない）。遊べるようになる前に「もう遊べる」と誤解させないため。
- N は半角数字で、桁区切りを付けない。単位は N の直後に付け、空白を入れない（「約5分」）。
- 「約」は目安であることを示す。N を増減しない。
- 日・週の単位は使わない。24時間以上も「時間」で出す（「約24時間」「約25時間」）。N に上限は設けない。
- 「明日」「今日中」「午前0時」「太平洋時間」など、日付・時刻・時間帯の語は使わない（基準7、復旧の時刻が日本時間の日付と一致しないため）。

境界値の例

| `Retry-After`（秒） | 画面の文 |
|---|---|
| 1 | あと約1秒で、もう一度遊べます。 |
| 59 | あと約59秒で、もう一度遊べます。 |
| 60 | あと約1分で、もう一度遊べます。 |
| 61 | あと約2分で、もう一度遊べます。 |
| 120 | あと約2分で、もう一度遊べます。 |
| 3540 | あと約59分で、もう一度遊べます。 |
| 3599 | あと約60分で、もう一度遊べます。 |
| 3600 | あと約1時間で、もう一度遊べます。 |
| 3601 | あと約2時間で、もう一度遊べます。 |
| 7200 | あと約2時間で、もう一度遊べます。 |
| 82800（23時間の日の残り程度） | あと約23時間で、もう一度遊べます。 |
| 86400 | あと約24時間で、もう一度遊べます。 |
| 90000（25時間の日の残り程度） | あと約25時間で、もう一度遊べます。 |
| 未設定・`0`・`abc` など | しばらくしてから、もう一度遊んでください。（説明は「サーバーの利用上限に達しました。」から始まる別の文。「文言」を参照） |

- 上の表の「画面の文」は説明の後半である。完全な文は「サーバーの利用上限に達しました。」を前に付ける。
- 3599 は「約60分」になる。基準7の「1時間未満は約N分」と「切り上げ」をそのまま合わせた結果である（「PO に示す事項」1）。

## 503 と 429 の表示規則の違い
同じ `Retry-After` を読むが、表示の規則は意図して分ける。

| 項目 | 503 `quota_exceeded`（この仕様） | 429 `too_many_requests`（25.md、変えない） |
|---|---|---|
| 表示場所 | QuotaNotice（panel を入れ替える） | FetchStatus の中の `.msg`（panel は残る） |
| 待ち時間の単位 | 秒・分・時間に変換する | 秒のまま（`3600` は「約3600秒」） |
| 端数 | 単位への変換で切り上げ | 丸めない（入力は整数だけ） |
| 文言 | 「サーバーの利用上限に達しました。あと約N<単位>で、もう一度遊べます。」 | 「操作が多すぎます。あと約N秒待ってから、もう一度試してください。」 |
| 使えない値のとき | 「サーバーの利用上限に達しました。しばらくしてから、もう一度遊んでください。」 | 「少し待ってから、もう一度試してください。」 |
| 操作 | 「ホームへ戻る」のみ | 入力と決定は残る（再送できる） |
| data-state | `quota` | `throttled` |

- 分ける理由：429 は数十秒で戻る想定で、検索をその場で続けられる。503 は数分〜1日待つため、遊びをやめてホームへ戻る前提で、読みやすい単位にする。
- 共通の変換関数に 429 を載せない。429 に分・時間の言い換えを入れると基準10と 25.md に反する。
- 両者は混ざらない。`classify` の分岐は別で、1つの応答がどちらにもなることは無い。

## 数字の表示規則（T2-1）
| 数字 | 加工 | 根拠 |
|---|---|---|
| 待ち時間 N（503） | 使える `Retry-After` の秒数を、60秒未満は秒、60秒以上1時間未満は分（切り上げ）、1時間以上は時間（切り上げ）にして整数で出す。桁区切りなし、使えない値は数字を出さない | 基準7、基準8、基準4 |
| 待ち時間 N（429） | 秒のまま、変えない | 基準10、25.md |
| 上限の残りのユニット数、使った量、上限の値 | 画面に出さない（本文にもヘッダにも来ない） | 基準5 |
| 復旧の時刻・日付 | 出さない | 基準7（「明日」を使わない） |
| 上記以外（お題、残り、合計、上限、目標、判定値、履歴の切り捨て値と実際の再生回数） | 変えない。#3・#4・#5 の表示規則のまま。QuotaNotice はこれらを変更も再計算もしない | 基準9（ゲームは進んでいない）。PO の言葉（「10,000未満は切り捨て…正しい数字も注釈で出しておく」）に反する数字は、この仕様に無い |

根拠の列が空の行は無い。

## 文言
- 見出し（h2）：いまは遊べません
- 説明（待ち時間あり）：サーバーの利用上限に達しました。あと約N<単位>で、もう一度遊べます。（N は半角数字、単位は秒・分・時間。例：「あと約1時間で」）

## アクセシビリティ
11.md のとおり。変える点と、確認する点は次のとおり。

- フォーカス：QuotaNotice が出たら、見出し（h2、`tabindex="-1"`）にフォーカスを移す。見出しの次の Tab で「ホームへ戻る」に着く。
- 読み上げ：フォーカス移動で見出し「いまは遊べません」が読まれ、続けて説明を読める（`<section aria-labelledby>`）。`role="alert"` も `aria-live` も足さない（二重に読まれるため）。説明の「約1時間」「約5分」は、数字と単位が空白なしでつながっていて、そのまま読み上げられる。
- 待ち時間は文の中の文字で伝える。色や図形だけに頼らない。新しい色は使わない。
- キーボード：ボタンは `<button type="button">`、Enter / Space で押せる。タブ順は、やめる、ホームへ戻る。
- タッチ：ボタンは高さ44px以上、幅いっぱい（11.md のまま）。
- 動き：アニメーションを足さない。カウントダウンの更新も無いので、読み上げが繰り返されることも無い。
- 360px 幅：説明は折り返す。固定幅を置かない。横スクロールを出さない。

| 429 `too_many_requests` ＋ 使える `Retry-After` | 「操作が多すぎます。あと約N秒待ってから、もう一度試してください。」（`data-state="throttled"`）。秒のまま、分・時間にしない。再試行なし。ゲームの状態は変えない。 | #25（サーバの契約は #7）。#32 は変えない（基準10） |
| 429 `too_many_requests` ＋ 使えない `Retry-After` | 「少し待ってから、もう一度試してください。」（`data-state="throttled"`）。 | #25 |

| 499 `canceled` | クライアントに届かない。画面側は、やめる・画面遷移で自分が中止した場合を `cancelled` として結果を捨てる（表示なし）。 | #3 |
| 502 `upstream_error` | 通信失敗（「取得に失敗しました。…」と「もう一度試す」）。ターンは減らない。 | #3 |
| 503 `quota_exceeded` ＋ 使える `Retry-After` | 「いまは遊べません」（QuotaNotice。panel を入れ替え、「ホームへ戻る」だけ）。説明「サーバーの利用上限に達しました。あと約N<単位>で、もう一度遊べます。」。単位は秒・分・時間。 | #32（表示の基本は #11、サーバは #10・#26） |
| 503 `quota_exceeded` ＋ 使えない `Retry-After` | 「いまは遊べません」（QuotaNotice）。説明「サーバーの利用上限に達しました。しばらくしてから、もう一度遊んでください。」。 | #32（基本は #11） |
| 503 で `code` が `quota_exceeded` 以外 | 従来の通信失敗。`Retry-After` は読まない。 | #3 |

## 仮定
- 基準7の「60秒未満は秒、1時間未満は分」は、サーバが返した整数秒 `s` で判定し、その後に単位ごとに切り上げる。そのため 3599 は「約60分」になる。
- 24時間以上は日にせず「約N時間」と出す。N に上限は設けない。基準7が「それ以上は約N時間」と定めているため。
- 使えない `Retry-After` の定義は、25.md の `parseRetryAfter` に揃えた。HTTP 日付形式は端末の時計に頼らないため使えないとした。基準8の「使える」の中身は基準に書かれていないので、この定義を置いた。
- 抑制中でも、上限到達でも、画面は区別しない。違いは `Retry-After` の長さだけで表れる。
- `data-retry-after` を `quota-notice` に付ける。テストで読み取った秒を確かめるためで、利用者には見えない。値は上限の残りや使った量ではなく、待ち時間の秒だけである。
- 待ち時間は応答時点の値で固定し、再計算しない。基準7に更新の定めが無く、25.md（429）の扱いに合わせた。
- 文言は句点で終える。読点の位置は基準のとおりで、足したり減らしたりしていない。

## PO に示す事項
基準の範囲内だが、根拠が基準に書かれていない判断である。

1. 3599秒（1時間にわずかに足りない）は「あと約60分」と出る。3601秒（1時間を1秒超える）は「あと約2時間」と出る。基準7の「1時間未満は分」と「切り上げ」を機械的に合わせた結果である。
   - 案：基準どおり。
   - 別案：分に切り上げて60分になるときは「約1時間」にする。
   - 案を変えたときの変更範囲：変換規則の表と境界値の例の表、変換関数、そのテスト。基準7の「1時間未満は約N分」の文言と食い違うので、PO が許す場合に限る。
2. 日付形式の `Retry-After`（HTTP 日付）を「使えない」として「しばらくしてから」の文を出す。基準4はサーバが整数秒を返すと定めているため、実害は無い。
3. 24時間以上は「約25時間」のように時間で出す（日にしない）。基準7の「それ以上は約N時間」に従った。
